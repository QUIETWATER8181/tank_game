# 新模式架构与逻辑契约

状态：数据与规则层、写实代理模型、3D 搭建交互、第一关布景与自由镜头、第一关实时战斗已接入。战斗表现与实时模拟在 `js/three/combat.mjs`，胜负判定仍只走 `js/mode/campaign.mjs` 的 `transitionRun`，`js/mode/` 未因战斗改动。操作步骤见 [界面检验指南](界面检验指南.md)。

## 1. 总体分层

```text
未来页面：模式大厅 → 车间 → 坦克仓库 → 关卡选择 → 战斗 → 结算
                         ↓
application.mjs：解锁、草稿、制造、关卡准备
            ↓                    ↓
evaluation.mjs              campaign.mjs
蓝图校验 / 数值评估          地图计划 / 互动规则 / 胜负状态
            ↓                    ↓
catalog.mjs：部件、类型、数值含义、版本、平衡参数
            ↓
storage.mjs + models.mjs：IndexedDB 存档 / GLB 资产仓库

表现层 js/three：
  workbench.mjs        页面状态、面板、快捷操作、自动保存
  build-interaction.mjs 3D 点选 / 拖动 / 吸附标记
  tank-model.mjs       程序化写实坦克代理
  level-scene.mjs      第一关地形、基地、敌我坦克、氛围动画
  runtime.mjs          渲染器、自由镜头、环境切换、固定步
  placement.mjs（js/mode）自动放置、网格吸附、重新连接（纯数据）
```

`js/mode/` 不依赖 DOM、Three.js 或渲染循环，能直接在 Node 测试。浏览器通过 `SteelJourneyCore` 使用同一套接口。加载 core.bundle.js 只定义接口，不自动建库、不开始战斗。渲染对象不作为游戏数值来源。

## 2. 三种必须区分的数据

| 数据 | 内容 | 保存位置 | 数值依据 |
| --- | --- | --- | --- |
| 模型资产 | GLB、名称、分类、格式、大小、不可覆盖的 ID | IndexedDB assets | 否，仅用于外观 |
| 搭建蓝图 | 坦克类型、部件实例、位置、朝向、连接、主武器 ID、修订号 | profiles.blueprints | 是 |
| 成品坦克 | 蓝图快照、可选模型 ID、评估报告和规则版本 | profiles.tanks | 入场前按蓝图重新计算 |

资产分类为 `terrain` 场地、`enemy-tank` 敌坦、`player-tank` 玩家坦克。列表仅返回元数据，取单个模型时才返回 Blob。资源 ID 当前不可覆盖，也不提供删除，避免静默破坏已有引用。GLB 仓库仅检查容器、版本、内嵌资源与压缩扩展，不保证任意模型可正确渲染或参与评估。

“模型评估”首先依据有语义的部件蓝图。任意导入的完整 GLB 无法可靠判断哪里是引擎、装甲或炮管，必须补充部件映射与碰撞代理后才可参与评估。装饰网格的面数、视觉大小和文件大小不直接增加攻击或防御。

## 3. 车间到坦克仓库的流程

1. 选坦克类型，按类型过滤部件目录。
2. 读取已解锁部件；免费部件默认开放，付费部件消耗“零件”永久解锁。
3. 放置部件：`suggestPlacement` 按角色生成候选位置（车体、炮塔、尾部、首上、侧面），逐个用结构校验挑选第一个不重叠且能连接的方案。车体、履带、引擎、炮塔各限一件；武器 1～4 件；装甲不限。
4. 在 3D 中拖动：位置按 0.1 / 0.25 m 网格或自由模式吸附；松手时 `nearestAttachment` 找 0.3 m 内最近的合法父件并更新 `parentId`，形成“自动重新连接”。Shift+拖动改高度，避免只能在地面平面移动。
5. 保存草稿（也可自动保存）。草稿允许未完成；修订号必须递增，拒绝过期覆盖。
6. 预评估：校验结构并返回错误、警告、指标、公式说明与数值。
7. 点击制造：在一次存档事务内重新检查解锁与蓝图，评估通过才写入成品。
8. 成品保存蓝图快照，之后改草稿不改变已造坦克。
9. 选成品进入第一关准备阶段，再次评估后生成独立关卡快照。

第一版只收取解锁费，不消耗放置库存，不收取制造费；这些是尚待调平衡的暂定规则。付费部件示例成本 30 / 40，不是最终价格。新模式钱包暂时独立，初始为 0；本轮不迁移或扣除旧小游戏钱包，也不增加可领取奖励。第一关奖励暂为 0。

同一部件重复解锁不会重复扣费。IndexedDB 读写事务将“扣费 + 解锁”原子提交，失败回滚，并覆盖多个标签页并发调用。MemoryRepository 用于测试，不是持久存储失败时的无提示替代品。

## 4. 部件与类型契约

首批规则数据：车体、履带组、引擎、炮塔、基础火炮、迫击炮、硬装甲板、速射炮、爆破发射器。尺寸按约 1 单位 = 1 米设计（车体 3.4 × 1.2 × 6.4 m），便于 3D 代理读起来像坦克。全部几何尺寸、质量和能力为游戏设计代理数据，后续由真实部件配置替换。

| 类型 ID | 中文 | 原型倾向 | 武器限制 |
| --- | --- | --- | --- |
| infantry | 步坦 | 均衡 | 基础火炮 |
| heavy | 重坦 | 高攻击、生命、防御；低移速攻速，体型质量影响转向 | 基础火炮 |
| assassin | 刺坦 | 快速、高伤害与攻速；偏好轻量结构 | 基础火炮、速射炮 |
| exotic | 奇坦 | 更宽的武器目录 | 所有当前武器 |
| artillery | 高坦 | 高生命、低防御，较慢移速攻速，范围攻击 | 主武器必须迫击炮 |

蓝图实例包含 `id / partId / parentId / position / yaw`。位置为车体坐标系下的绝对坐标，`parentId` 仅表示连接拓扑，**不是层级局部变换**。Y 朝上、+Z 向前、单位米，yaw 为弧度。当前不允许缩放、俯仰与侧倾；后续增加此能力需要升级蓝图版本及碰撞检查。

炮塔是可选部件：有炮塔时武器可挂在炮塔上并拥有独立炮塔转向；无炮塔时武器直接固定在车体上（自行火炮/歼击车），评估会给出提示。炮塔最多一个，不要求存在。

必须有唯一车体、一个引擎、一组履带、1～4 个武器，明确指定主武器；不存在连接、循环连接、悬空连接、穿地或明显重叠会拒绝制造。当前使用旋转后的轴对齐包围盒，复杂斜面可能被保守地判为碰撞，后续应替换为连接插槽与凸体碰撞检查。

## 5. 评估过程与边界

顺序：结构校验 → 汇总部件质量/功率/装甲 → 计算包围尺寸与重心 → 检查履带支撑 → 计算稳定性与类型适配 → 输出数值和武器列表。

- 移速：功率 / 质量 × 类型系数 × 稳定性 × 适配修正，并限制上限下限。
- 扭转速度：受总质量、水平尺寸、类型及稳定性共同影响。
- 炮塔转向：仅在有炮塔时输出，受炮塔质量、总质量、类型系数与稳定性影响。
- 生命：车体与装甲生命值总和 × 类型系数。
- 防御：车体与硬装甲评分总和 × 类型系数；原型伤害公式为 `原始伤害 × 100 / (100 + 防御)`。
- 攻击：每件武器基础伤害 × 类型系数 × 适配修正。
- 攻速：每件武器基础频率 × 类型系数，单位次/秒。
- 类型适配：当前以设计质量偏好近似，修正范围有限，不会因跨风格搭建把能力直接归零。

`stats.attack / fireRate / projectile` 相关字段以主武器为准；`weapons[]` 保留所有武器独立数值、安装位置、朝向和 `onTurret`。未来不能把主武器数值直接套到副武器，也不能把所有武器频率简单累加。

子弹数据拆成初速 `launchSpeed`、下落加速度 `gravity`、寿命 `lifetime`、爆炸半径 `blastRadius`、迫击炮设计命中延迟 `impactDelay`。射程还受发射角和出生高度影响。本轮只定义数据，不实现弹道与伤害判定。

尚未实现炮口遮挡、射界、承重、真实接地、正侧后装甲、部位破坏、动力传递与供能。评估报告始终标为原型；校验通过不代表已经通过真实物理验证。

## 6. 表现层：写实代理、搭建交互与第一关布景

### 6.1 程序化坦克代理

`tank-model.mjs` 按蓝图逐个部件生成 Three.js 节点，所有尺寸来自 `PARTS`，因此模型与评估使用同一份数据：

- 车体：侧面轮廓挤出（首上倾斜、尾部收缩）、首上附加装甲与铆钉、驾驶员舱盖/潜望镜、车灯与护框、拖钩、挡泥板、侧裙、随车工具、备品、拖缆、后部舱门。
- 履带：54 节履带板合并为一条带子、5 对负重轮、主动轮（带齿）、诱导轮、托带轮、悬挂臂、翼子板与挡泥皮。
- 引擎：动力舱、散热格栅、进气口、排气管与隔热罩、冷却风扇。
- 炮塔：座圈、倾斜炮塔壳、尾部篮筐、防盾与帆布罩、指挥塔/舱盖/潜望镜、高射机枪、炮长镜、烟幕发射器、天线、备品与侧标。
- 武器：基础火炮（后座套、炮管、抽烟装置、炮口制退器、并列机枪）、速射炮（四联装）、爆破发射器（定向管束）、迫击炮（座钣、身管、双脚架、瞄具）。
- 装甲：带铆钉和加强筋的附加板。
- 玩家/敌坦/守卫/残骸使用四套配色；合并按“每个部件按材质”或“整辆按材质”两级，前者保留点选，后者把单辆坦克压到约 11 次绘制。

### 6.2 搭建交互

- `createBuildInteraction` 在视口捕获指针事件：悬停改光标，按下点选并锁定 OrbitControls，移动时在部件高度平面求交，松手提交。合成/失效指针不会让捕获异常中断拖拽。
- 选中标记由包围框线框 + 地面圆环组成，不修改共享材质，因此不会把同一材质的所有部件一起染色。
- `placement.mjs` 是纯数据：`suggestPlacement`、`moveCandidate`、`nearestAttachment`、`snapValue` 可独立测试。
- 撤销/重做保存 60 步蓝图快照；自动保存防抖 0.9 秒，修订号递增；`saving` 期间的新改动排队，避免并发写冲突。

### 6.3 第一关布景与镜头

`level-scene.mjs` 是确定性的（固定随机种子），不读取外部资源：

- 地形：程序化草地贴图、路面与路肩、边线、虚线、车辙、石块/灌木（InstancedMesh）、反光路桩、两座瞭望塔；可碰撞掩体（残骸/沙袋/土堤/木箱/弹药堆）与泥地、碎石区按 `map.cover` / `map.zones` 生成，每种掩体一个 InstancedMesh。
- 基地：围墙与 12 m 大门、警示条、指挥地堡、旗杆（顶点波动动画）、雷达（旋转）、油桶、探照灯；基地被摧毁后旗与雷达消失并出现浓烟。
- 敌我坦克：按模板蓝图生成 5 辆；玩家在 `combat: true` 时保留部件组（炮塔 + 俯仰枢轴），敌坦/守卫整辆合并、用整车转向瞄准；被消灭后替换为倾斜残骸并冒烟。
- 氛围：渐变天空球、远山脊线、雾、尘埃粒子、道路触发标记；场景注册固定步系统，每帧更新旗帜、烟、雷达和尘埃。
- 镜头：OrbitControls 自由环绕（360° 方位、0.02～0.495π 俯仰、阻尼、右键平移、滚轮缩放），关卡内 W/A/S/D/Q/E 平移；`focusOn` 做缓动定位，关卡提供玩家、全景、基地、每辆敌坦的取景点；自动环绕模式。开战后相机改为第三人称跟随（`camera = 车体后方 12.5 m / 高 6.2 m`，看向车体前方 16 m），`controls.enabled = false`，战斗结束恢复。

## 7. 第一关数据与胜负逻辑

地图：宽 36 米、长 180 米的三段式走廊（`generator: 'corridor-v2'`），+Z 前进，分为 9 个 20 米段；`map.cover` 是可碰撞掩体，`map.zones` 是只改移速的地形区。缺省字段由 `normalizeLevel()` 补齐，旧存档照常加载。

| 对象 | 位置 X / Y / Z | 意图 | 触发进度 Z |
| --- | --- | --- | --- |
| 玩家 | 0 / 0 / 8 | 初始出生 | — |
| 途中敌坦 1 | 0 / 0 / 42 | 正面对抗（残骸后） | 25 |
| 途中敌坦 2 | -11 / 0 / 120 | 左侧偷袭（泥地缺口外） | 78 |
| 途中敌坦 3 | 11 / 0 / 120 | 右侧偷袭（碎石缺口外） | 78 |
| 终点守卫 | 0 / 0 / 150 | 守卫基地大门 | 132 |
| 敌方基地 | 0 / 0 / 170 | 无主动效果、150 原型生命 | — |

敌坦模板采用三辆步坦和一辆重坦守卫，后续可配置独立敌方模型和蓝图。AI 实现在 `js/three/combat.mjs`：待机 → 触发（玩家越过 `triggerZ` 或距离 ≤ 26 m）→ 转车体、保持 22 m 推进 → 夹角 < 0.16 rad 且距离 < 62 m 时开火。玩家和敌人都由同一套评估规则生成能力。

状态：`ready → running → victory / defeat`。应用服务只准备 `ready`，不自动开始；测试通过显式事件驱动。敌人重复销毁事件幂等，未知敌人拒绝，终局拒绝继续写事件。

胜利：基地被摧毁 **并且** 4 个敌人全部销毁。只打基地或只清敌都不胜利。玩家销毁进入失败。同一模拟步内的判定顺序由 `CombatSim.checkOutcome` 固定为「先判玩家阵亡，再判胜利」，也就是同帧双亡按失败处理。战斗接入后，销毁事件只来自模拟层（`CombatSim.damageUnit`）；UI 的「规则自检」按钮仍然可以手动发事件，但它只是开发工具，联机时不能由客户端宣告胜利。

结算回到关卡选择；下一关当前禁用并显示“后续关卡待开发”，不跳转空页面。失败可重新准备。默认关闭友伤，预留同队与友伤参数；组队、碰撞、推挤和联网同步尚未运行。

## 8. 持久化与版本

IndexedDB 名 `steel-journey-3d`，数据库版本 1；profiles 存钱包、解锁、草稿与成品，assets 存 GLB。不同站点/端口拥有不同存储；file:// 下是否可存由浏览器决定，稳定开发建议 HTTP。不要宣称这里的存档已经云同步。

蓝图及存档 schemaVersion 为 1，评估规则为 prototype-2。未知存档版本报错并保留原数据，不清库重建。将来升级要显式迁移；进入关卡会用当前规则重新评估，不信任旧的派生数值。

旧草稿（prototype-1 时代）没有炮塔，仍可载入并通过校验：炮塔是可选部件，旧蓝图会以“无炮塔”形式继续使用，只是武器随车体转动。

当前没有跨设备同步、存档导入导出、资产垃圾回收、容量管理或防作弊。仓库模型和成品拆开保存，避免把大 Blob 重复写进每辆坦克。模型导入是显式操作，实际创建 ObjectURL 后仍应由表现层负责 revoke，场景对象由现有 resources.mjs 释放。

## 9. 接入示例与验证

```js
// 浏览器已加载 core.bundle.js；Node 使用 import * as Core from './js/mode/index.mjs'
const Core = SteelJourneyCore;
const repository = await Core.openRepository();
const app = Core.createApplication(repository);
const blueprint = Core.createStarterBlueprint('infantry', 'my-draft');
await app.saveDraft(blueprint);
const report = await app.evaluate(blueprint);
const tank = await app.manufacture({ blueprintId: blueprint.id, tankId: 'my-first-tank' });
const preparedRun = await app.prepareFirstLevel(tank.id);
// preparedRun.status === 'ready'；这里没有启动模拟或渲染。
app.close();
```

重复使用示例前需换草稿/坦克 ID；修改现有草稿需增加 revision。正式 UI 应集中管理一个 repository 生命周期，避免每个组件分别开库。

`npm run test:3d` 覆盖类型评估、非法结构、解锁扣费、草稿冲突、成品快照、入场重评、第一关胜负、自动放置/吸附、程序化模型尺寸与合并、关卡布景与资源释放，以及原有运行时。
